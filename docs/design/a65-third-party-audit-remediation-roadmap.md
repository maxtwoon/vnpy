## A65 — Fix Failing Test + Harden `capture_window` Against Missing Capture Metadata

### Rationale
`simnow_strategy_surface.py:157`'s `build_strategy_surface_from_captured_session` unconditionally
calls `capture_window(capture.get("meta") or {})` (added by the parallel `fb18b45e` commit, not
this session's A61-A64 work), and `capture_window` (line 39-42) does `meta["started_at"]` with no
`.get()`/default — a bare `KeyError` for any capture payload lacking these keys.
`test_simnow_consistency_source.py`'s `test_build_strategy_surface_from_captured_session_uses_real_
callbacks` fixture (dating to A41, before `fb18b45e`'s change) constructs a capture dict without
`meta` at all, so it now fails. Confirmed via `simnow_daily_capture.py` that production captures
always populate `started_at`/`ended_at` — this is a test/robustness gap, not a live-capture risk,
but it currently blocks `pytest examples/czsc_strategy/tests/unit -q -m "not realdb"` from passing
cleanly and must be fixed before any other task in this roadmap lands (a red test suite makes it
hard to trust later tasks' own "existing tests pass byte-identical" claims).

### Semantics
Make `capture_window` tolerant of missing `started_at`/`ended_at` — either (a) return a sentinel
(e.g. `("", "")` or `(None, None)`) when either key is absent, with callers treating that as "window
unavailable" rather than crashing, or (b) keep `capture_window` strict but have
`build_strategy_surface_from_captured_session` catch the missing-key case explicitly and omit
`window_start`/`window_end` from its `meta` output in that case. Either is acceptable; pick based on
which keeps `build_strategy_surface_from_capture`'s (the OTHER, older caller at line 65) existing
behavior unaffected — that caller's own tests must stay byte-identical. Additionally, decide whether
the now-outdated `test_simnow_consistency_source.py` fixture should be updated to include
`started_at`/`ended_at` (matching real production captures) in addition to, or instead of, making
the function more tolerant — the design step for this task should re-read that test's original
intent (A41's captured-session authenticity check) before choosing.

### No-lookahead & correctness
Pure defensive-coding fix; no new data read, no timing change, no SimNow order/cancel/send path
touched.

### Expected files

  `build_strategy_surface_from_captured_session`)
- `examples/czsc_strategy/tests/unit/test_simnow_consistency_source.py` (fix the fixture and/or add
  a case for the missing-metadata path, whichever the dev-round's design decision calls for)

## A67 — Limit/Halt "Unexecutable-Fill" Backtest Mode

### Rationale
`limit_halt_model="aware"` (shipped by A51, extended by A57/A59/A61) only tags whether a fill bar
was at/beyond the daily limit band — it never changes whether that fill actually happens, per the
config comment's own words ("without changing fills, prices or trade counts"). This is a genuine,
intentional design boundary from A51 onward (tagging-only, by design, to keep the mode
byte-identical-safe) — but the audit's point is that NO mode currently answers "what would this
backtest's numbers look like if unexecutable fills were rejected or deferred instead of silently
allowed?" This is a real behavior-mode gap, not a bug in the existing tagging logic.

### Semantics
Add a new value to `limit_halt_model` (e.g. `"enforce"`, alongside existing `"off"`/`"aware"`) that,
when a bar's fill would occur at or beyond the price-limit band (using the same `_bar_at_limit`
directional logic A59 already built), defers the fill to the next bar where it's no longer at the
limit (a queued/pending-fill model) — or, if the design step decides deferral is too complex for a
first cut, simply skips/blocks the fill for that bar and logs it as `fill_rejected_at_limit` (a
simpler, more conservative first implementation; deferral can be a follow-up if the simpler version
proves the concept). This task's own design step must pick one and justify the choice — read A59's
`_bar_at_limit`/directional-touch work in full first, don't re-derive it from scratch. `"off"` and
`"aware"` must remain byte-identical to their current behavior; `"enforce"` is a new, clearly
opt-in, clearly-labeled research mode.

### No-lookahead & correctness
Deferred/rejected fills must only use information available at or before the bar being evaluated —
no peeking at future bars to decide "when would this have been fillable." If deferral is chosen,
the deferred fill must execute at the NEXT bar's price once fillable, not retroactively adjust the
original bar's numbers.

### Expected files
- `chan_strategy/backtest_engine.py` (fill-execution path, gated behind the new `"enforce"` value)
- `chan_strategy/positions.py` (if fill deferral requires new state on `Position`)
- `chan_strategy/config.py` (new `limit_halt_model` value documented)
- `tests/unit/test_limit_halt_aware.py` (or a new `test_limit_halt_enforce.py` — decide based on
  scope; likely large enough to warrant its own file)
- A new diagnostic report comparing `"off"`/`"aware"`/`"enforce"` outcomes (RESEARCH-ONLY banner,
  reusing `declassify_historical_reports.build_banner()`)

### Acceptance (decidable)
- [ ] `limit_halt_model="off"` and `"aware"` remain byte-identical to current behavior (existing
      equivalence tests untouched).
- [ ] `limit_halt_model="enforce"` is unit-tested: a fixture bar at the limit band produces a
      rejected/deferred fill (not the current silent-allow behavior), with no lookahead (a fixture
      proving the decision uses only current-and-prior-bar information).
- [ ] A comparison report (RESEARCH-ONLY banner) quantifies how much `"enforce"` changes reported
      trade counts/PnL relative to `"aware"` on the same post-2026-04-24 window — reported as honest
      measurement, not a superiority claim.
- [ ] No threshold tuning; no pre-2026-04-24 data used for any parameter choice; no SimNow
      order/cancel/send path changed; no `GOAL PASSED`.
- [ ] Full unit suite, root + child `sync_check`, preflight pass.

### Boundaries
Does not change `"off"`/`"aware"`'s existing semantics at all. Does not attempt to model actual
exchange queue position or partial-fill-at-limit microstructure — a binary
reject-or-defer-whole-fill model is sufficient for this task; finer-grained partial-fill modeling is
a possible future task, not this one's scope.

### Dev prompt

## A69 — OOS / Parameter-Perturbation / Cost-Sensitivity Minimum Gate (Own Sub-Design)

### Rationale
The audit's own framing is directional, not a fully-specified mechanism: "give out-of-sample
testing, parameter perturbation, and cost/slippage sensitivity a minimum gate." This is the
largest and least-specified item in the roadmap — no existing code location, exact threshold, or
test fixture was cited by the audit, unlike items #1-#4 above. Treat this task's OWN promotion as
requiring a real design step (not just an implementation handoff) before any code is written.

### Semantics (to be finalized during this task's own design step — this is intentionally
under-specified here, mirroring how A56/A59 handled genuinely open judgment calls)
At minimum, this task's design step should determine:
1. What "OOS" means operationally in this codebase already — `backtest_matrix_report.py` already
   has `DEFAULT_IS_START`/`DEFAULT_IS_END`/`DEFAULT_OOS_START`/`DEFAULT_OOS_END` constants
   (confirmed present) — read how they're currently used before assuming a new mechanism is needed;
   the gap may be "no gate enforces that OOS results are checked/reported," not "no OOS split
   exists at all."
2. What a "parameter perturbation" gate would concretely check — e.g. re-running with ±10-20% on
   a small set of already-tunable parameters (`atr_trail_mult`, `partial_tp_frac`, stop-loss
   percentages) and asserting the qualitative conclusion (sign of expectancy, pass/fail of some
   existing threshold) doesn't flip — vs. a full grid search (likely too expensive/out of scope for
   a "minimum gate").
3. What "cost/slippage sensitivity" minimally means — e.g. re-running the same backtest at 1.5x/2x
   the configured `commission_rate`/`slippage` and reporting how much the headline numbers move,
   without necessarily gating pass/fail on a specific threshold (a measurement gate, not
   necessarily a hard pass/fail gate, may be the appropriate "minimum" bar here).

work, recorded in the Decision Log BEFORE implementation — mirroring A56's "decide, then implement"

when evaluating that window's own results; perturbation/sensitivity re-runs must use the same
